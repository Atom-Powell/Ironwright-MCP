# PhishMaster MCP Enhancement: Architecture & Build-vs-Augment Decision (Copilot Studio, September 2026)

## TL;DR
- **Build a new, purpose-built custom MCP server** — do not fork a community SharePoint MCP project. None of the existing open-source servers implement the reconciliation engine, single-call recursive tree inventory, or bulk rename/move planning PhishMaster needs; they are thin per-call Graph wrappers that reproduce exactly the ID-navigation, recursive-enumeration-cost, and stale-ID pain you already have. The reconciliation logic (workbook expected-state vs. repository actual-state) is your differentiator and must be your own deterministic code.
- **The decisive new fact since your last research:** Microsoft now ships a **first-party "Work IQ SharePoint" MCP server** (via Agent 365 / Work IQ MCP; the underlying Work IQ API reached GA June 16, 2026) exposing ~30 governed tools — but its file surface is document-management primitives (search, get metadata, upload, copy/move, lists), **not** batch tree inventory or reconciliation, and the MCP tool layer is **preview**, gated behind a Microsoft 365 Copilot license, with a **5 MB file read cap** and no Excel-workbook-as-database capability. Use it as a complementary, governed primitive layer if you already hold Copilot licenses, but it does not solve the reconciliation problem.
- **Recommended stack:** TypeScript + official MCP SDK (`StreamableHTTPServerTransport`, stateless mode) + Microsoft Graph JS SDK, hosted on **Azure Container Apps** (or Azure Functions Flex Consumption), fronted by a Power Platform custom connector for Copilot Studio, using **path-based Graph addressing + `$batch` + delta query + Excel persistent sessions** and a lightweight external state index (Azure Table Storage or SQLite/Cosmos). Prefer Node-native Azure hosting over your usual Cloudflare Workers for this Graph/Excel-session-heavy workload.

## Key Findings

### 1. Copilot Studio MCP mechanics (September 2026)
- **Transport:** Copilot Studio supports **only Streamable HTTP** for MCP. Per Microsoft Learn ("Connect your agent to an existing MCP server," doc dated 2026-05-28): *"Copilot Studio no longer supports SSE for MCP after August 2025."* stdio is not usable (it is local-only). Your server must expose an HTTPS POST `/mcp` endpoint speaking Streamable HTTP (JSON-RPC).
- **Two onboarding paths:** (a) the **MCP onboarding wizard** — Agent → Tools → Add a tool → New tool → Model Context Protocol → supply Server name/description/URL + auth; (b) the **Power Apps custom connector** path — import an OpenAPI 2.0 (Swagger) spec tagged `x-ms-agentic-protocol: mcp-streamable-1.0` on the `/mcp` POST operation. Both ultimately create a **Power Platform custom connector + connection reference** behind the scenes. (Microsoft Learn; microsoft.github.io/mcscatblog "Five Minutes to Your First MCP Connector," 2025–2026.)
- **Authentication:** wizard offers **None, API key** (header or query), or **OAuth 2.0**. OAuth supports dynamic client registration via a discovery endpoint, dynamic registration with manual authorization/token URLs, or fully manual client ID/secret — Copilot Studio supplies the OAuth callback URL. For an Entra-protected server the documented enterprise pattern is **Azure API Management as an OAuth 2.0 front door** for the MCP server. (Microsoft Community Hub deployment guide; developerscantina.com series, 2025–2026.)
- **Prerequisites & limits:** **Generative orchestration must be enabled** (classic orchestration ignores MCP). Per Microsoft Learn "Add tools to custom agents" (doc dated 2026-01-29): *"When using generative orchestration, the orchestrator can handle a maximum of 128 tools per agent. For best performance and results, however, we recommend limiting the number of tools in your agent to no more than 25-30."* Tools are **dynamically discovered** — server-side tool changes reflect automatically without republishing the agent.
- **Governance:** because MCP rides the connector framework, it inherits **Power Platform DLP, Advanced Connector Policies (ACP, GA June 4, 2026), VNet integration, and managed auth**. Critically for your architecture philosophy: **DLP/ACP granularity is per-server (allow/block the whole connector), NOT per-tool**. Per Microsoft's mcp-add-components-to-agent doc (dated 2026-05-15), all tools are turned on by default when you add a server and **makers can toggle individual MCP tools off** — i.e., tool-level control is a maker convenience, not a platform-enforced security boundary. This confirms your carried-forward assumption remains true as of mid-2026.
- **Cross-environment limitation:** Power Platform requires custom connectors to live in **their own solution** to move across environments; the MCP wizard adds the connector to the agent's solution, so you must separate it before deploying to another environment. (microsoft.github.io/mcscatblog, 2025–2026.)

### 2. What "SharePoint MCP" options actually exist
**Microsoft first-party:**
- **Work IQ SharePoint MCP server** (Agent 365 / Work IQ MCP). Tool surface (~30 tools): findSite, resolve site by path, list subsites, list document libraries (drives), get/create lists, add/update list items, column definitions, folder creation, file read/write (text + binary, **capped at 5 MB**), get metadata by ID or sharing URL, search files/folders across accessible sites, copy/move files asynchronously across libraries, sharing/sensitivity labels. **Preview** MCP tool layer; the underlying Work IQ API reached **GA on June 16, 2026** with **usage-based billing independent of Copilot licensing**, but access **requires a Microsoft 365 Copilot license**. Reachable in Copilot Studio, Microsoft Foundry, and (via `agent365.svc.cloud.microsoft`) developer clients. (Microsoft Learn "Work IQ MCP overview," ms.date 2026-08-10; "Work IQ SharePoint reference," preview.)
- **Microsoft MCP Management Server** (Agent 365) — an API-first surface to build/register your own custom MCP servers with connectors/APIs/custom logic. This is the "official blessed" path to plug in a custom server under central governance.
- **Microsoft MCP Server for Enterprise** (github.com/microsoft, public preview) — read-only Entra/directory scenarios via `microsoft_graph_suggest_queries` / `microsoft_graph_get`; **not** a SharePoint file-ops server. There is **no first-party general-purpose Microsoft Graph MCP server** for SharePoint file operations beyond Work IQ.
- **SharePoint Embedded MCP Server** (github.com/microsoft/SharePoint-Embedded-MCP-Server) — preview, for SPE containers, not classic document libraries; not applicable to your site/library.

**Community / open-source (all thin per-call Graph or SharePoint-REST wrappers, Claude-Desktop-oriented, stdio-first):**
- **Lokka** (merill/lokka, MIT) — the most-used community Microsoft Graph MCP server. Per PulseMCP's listing: *"GitHub Repo (271 stars)… Est. Visitors 18.5k (988 this week)… Released On Mar 15, 2025… Popularity Ranking #1,058"* (the live repo now shows ~295 stars). Generic Graph query/manage bridge; stdio transport; not SharePoint-repository-specialized; no batch tree/reconciliation.
- **DEmodoriGatsuO/sharepoint-mcp** (Python, Graph API) — site info, libraries, read DOCX/PDF/XLSX/CSV, full-text search, list/page/site provisioning; stdio/SSE/streamable-http.
- **sekops-ch/sharepoint-mcp-server** (TypeScript, MPL-2.0) — service-oriented, OAuth2 client-credentials, per-call Graph wrapper.
- **ncdcdev/sharepoint-docs-mcp** (search-only, cert auth), **Zerg00s/server-sharepoint** (SharePoint REST, client-secret app-only that stops working after April 2026), **peacockery-studio/sharepoint-mcp** (folder/doc ops, OAuth), **ravikant1918/sharepoint-mcp**, **ftaricano/mcp-onedrive-sharepoint** (10-tool "core" profile).
- **Assessment:** every community server is architected as **individual Graph/REST calls per operation** — exactly the model that produces your recursive-enumeration cost, ID-based navigation overhead, and stale-ID errors. None implement batch tree inventory, reconciliation, bulk rename/move planning, structure validation, or template replication. Forking any of them means adopting an unfamiliar codebase and its transport/auth assumptions (several are stdio-first / Claude-Desktop-oriented) while still writing 100% of your differentiating logic yourself.

### 3. Augment vs. build — decision
**Recommendation: Build new.** Reasoning:
- **Architectural mismatch:** the pain points are not "missing tools," they are "wrong granularity." Community servers expose 1 Graph call per tool; you need **composite, server-side orchestrated tools** (one `inventory_tree` call that internally fans out `$batch`/delta; one `reconcile_workbook_vs_repository` that reads Excel + walks the repo + diffs). No existing server has this shape, so forking saves little.
- **The reconciliation engine is bespoke domain logic** — it encodes your workbook schema, naming standard (`YYYY-MM_Client_MonthlyTraining.xlsx`), and folder taxonomy (Year → Client → Month). This cannot be inherited from any generic server.
- **Determinism/auditability (your stated philosophy):** owning the code lets you make every tool a discrete, deterministic operation returning a structured plan the LLM does not improvise — e.g., `generate_rename_plan` returns a reviewable diff, `execute_rename_plan` applies it verbatim. A third-party agentic server works against this.
- **Maintainability risk:** most community candidates are single-maintainer hobby projects; building on one couples your production stewardship agent to its release cadence and its April-2026-style auth deprecations.
- **Where augment still makes sense:** if you already own Microsoft 365 Copilot licenses, add the **first-party Work IQ SharePoint MCP server** alongside your custom server for governed, low-code primitives (search, sharing, sensitivity labels) — let your custom server own inventory/reconciliation/bulk ops and Work IQ own ad-hoc file primitives. This is complementary, not a substitute.

### 4. Graph API performance techniques that solve the pain points
- **Path-based addressing kills the ID-navigation pain (Pain Points #5, #6).** Graph driveItems can be addressed two ways: by ID (`/drives/{id}/items/{item-id}`) **or by path** (`/drives/{drive-id}/root:/Year/Client/Month/file.xlsx`). Designing your server around **path addressing** eliminates most discovery/traversal round-trips and makes operations resilient to stale IDs (a stale ID returns `NotFound`; a path re-resolves naturally). (Microsoft Learn, driveItem resource, 2026.)
- **`$batch` (Pain Point #1):** Per Microsoft Learn ("Combine multiple HTTP requests using JSON batching"): *"JSON batch requests are currently limited to 20 individual requests… Requests in a batch are evaluated individually against the applicable throttling limits and if any request exceeds the limits, it fails with a status of 429."* Combined payload is capped at 4 MB; `dependsOn` allows ordering; the Graph SDKs auto-split >20 into multiple batches. Batching folder-children reads collapses hundreds of calls into tens.
- **Delta query (Pain Point #1, "what changed since last scan"):** `/drives/{id}/root/delta` (and `/drives/{id}/list/items/delta`) returns an initial full crawl plus an `@odata.deltaLink` to fetch only subsequent changes — the documented best practice for scanning drives at scale without full re-enumeration. Store the deltaLink in your state index and re-scan incrementally. (Microsoft Learn, delta-query-overview + OneDrive scan-guidance, 2026.)
- **Search-based discovery (Pain Point #2, folder≠report):** the **Microsoft Search API** (`POST /search/query`, `entityTypes: ["driveItem"]`) and the per-drive `root/search(q=...)` endpoint let you find actual files by name/content anywhere in the library — including files sitting in a client root instead of a dated folder — without walking the tree. Supports KQL scoping like `path:` and `ParentLink:`. (Microsoft Learn, search-concept-files, 2026.)
- **Excel Workbook API as a database (Pain Point #7):** read worksheets/tables/named ranges as structured data via `/drive/items/{id}/workbook/...`. **Always use a persistent session** (`POST .../workbook/createSession` with `persistChanges:true`, pass `workbook-session-id` header on every call) — Microsoft states this is the most efficient mode. Persistent sessions expire after ~5 min of inactivity (non-persistent ~7 min); a stale session returns **404**, so detect and recreate. Per Microsoft Learn "Microsoft Graph service-specific throttling limits," Excel limits are *"5000 requests per 10 seconds per app (all tenants) and 1500 requests per 10 seconds per app per tenant… To reduce throttling and related failures, avoid high concurrency against the same workbook… For each workbook, send the next request only after receiving a successful response to the current request, especially for write operations."* Real-world 429s appear far sooner on heavy range/insert ops — honor `Retry-After`. The `.xls` format is unsupported (Open XML only).
- **Resilience (Pain Point #6):** use `@microsoft.graph.conflictBehavior` (`fail`/`replace`/`rename`) on create/move; note a documented quirk where `replace` behaves inconsistently for folders vs files. Combine path addressing + conflictBehavior + `Retry-After` handling for deterministic, resumable operations.

### 5. Recommended custom MCP server architecture
- **Language/SDK:** TypeScript + **official MCP TypeScript SDK** (`@modelcontextprotocol/sdk`) using `StreamableHTTPServerTransport` in **stateless mode** (`sessionIdGenerator: undefined`) so it scales behind a plain load balancer with no session affinity — Microsoft's own Node ACA tutorial uses exactly this. Create a **new McpServer/transport instance per request** (MCP TS SDK ≥ v1.26.0 enforces this to prevent cross-client data leakage). Use the **Microsoft Graph JS SDK** for Graph calls.
- **Hosting — prefer Node-native Azure over Cloudflare for this workload:**
  - **Azure Container Apps** is the recommended primary host (Microsoft Learn "Host MCP servers on Azure Container Apps," ms.date 2026-02-19; Node tutorial with `StreamableHTTPServerTransport`). Run stateless, min replicas = 1 to avoid cold starts, add a **GET `/health`** endpoint (probes are GET; MCP is POST), transport ingress `auto`. Avoid sticky sessions unless you go stateful (ACA affinity works only in single-revision mode via HTTP cookie).
  - **Azure Functions Flex Consumption** is a strong scale-to-zero alternative — Microsoft's **self-hosted remote MCP server on Azure Functions** (public preview, ms.date 2025-10-30, Ignite 2025) supports stateless streamable-HTTP servers built with the Node MCP SDK deployed as custom handlers; official sample `Azure-Samples/mcp-sdk-functions-hosting-node`. Flag: **preview, not GA**.
  - **Azure App Service** works too (`az webapp up`, Easy Auth for OAuth; official Node samples migrated from SSE to streamable HTTP) but watch the **~4-minute idle timeout** on long streams.
  - **Cloudflare Workers (your usual preference) is viable but not the best fit here.** The legacy `McpAgent`/Durable Objects path is now **deprecated/feature-frozen** (Cloudflare docs: "do not create a new McpAgent server"); the current path is the stateless `createMcpHandler`. For a Graph-heavy workload you'd need the **Paid plan** (Free CPU cap is 10 ms/request; Paid default 30 s, raisable to 5 min). Outbound Graph `fetch()` calls fit within subrequest limits (Paid default 10,000/invocation since 2026-02-11), but the **6-simultaneous-outgoing-connections/request** ceiling constrains parallel Graph fan-out, and the stateless handler has **no protocol-level session**, so you must externalize the Excel `workbook-session-id` and delta state into KV/D1/Durable Object storage yourself. Net: Azure Node hosting keeps you closer to the Graph/Excel-session model with less friction. (Cloudflare Workers limits doc, "Last updated Jul 28, 2026.")
- **Entra ID app registration & permissions:** register a confidential client. For an autonomous, deterministic steward that runs repository-wide operations, **application permissions** give predictable, user-independent behavior. Prefer **`Sites.Selected`** scoped to the Technology Success site (granting the app access only to that specific site) over `Sites.ReadWrite.All` + `Files.ReadWrite.All`, to satisfy your SMB least-privilege posture. If per-user identity/audit trails are required, use delegated + OAuth on-behalf-of, accepting that Copilot Studio's default is end-user credentials.
- **State/caching layer:** maintain a lightweight last-known-repository index to avoid full re-scans. **Azure Table Storage** (cheapest, schemaless, fits "store deltaLink + file inventory rows") is the pragmatic choice; **Cosmos DB** if you want richer queries; avoid **Dataverse** here unless you already run it for the agent's state (heavier, licensed). SQLite is fine only if single-instance. Store: per-drive `@odata.deltaLink`, last inventory snapshot (path, name, type, size, modified), and reconciliation results.
- **Tool design (discrete, deterministic, auditable — matches your philosophy):**
  - `inventory_tree(site, library)` → full tree with metadata in one call (internally `$batch` + delta).
  - `reconcile_workbook_vs_repository(workbook, library)` → reads Phish Threat Workbook (Active) via Excel session, computes expected deliverables, diffs against actual repo state, returns structured {missing reports, missing folders, naming violations, misplaced files, compliance status}. **Highest-value tool.**
  - `generate_rename_plan` / `execute_rename_plan` (two-phase: plan is reviewable, execution applies verbatim).
  - `generate_move_plan` / `execute_move_plan` (by rule/client/month/type).
  - `validate_structure(client)` → compliant/non-compliant/missing against the approved standard.
  - `replicate_template(sourceClient, targetClients)` → apply a validated client's structure (e.g., "4UCU") across clients.
  - `query_repository(question)` → answers operational questions (empty folders, orphaned files, recent reports) from the state index without recursive traversal.
  - Keep plan-then-execute separation so the LLM never improvises destructive operations — it calls `execute_*` only against a plan your code produced.

### 6. Publishing/installation path in Copilot Studio
1. **Deploy** the server (ACA/Functions/App Service) with an HTTPS `/mcp` Streamable HTTP endpoint + OAuth 2.0 (Entra) or API key.
2. **Register in Copilot Studio** via either: (a) the **MCP wizard** (Tools → Add a tool → New tool → Model Context Protocol → URL + auth), or (b) **Power Apps custom connector** importing an OpenAPI 2.0 spec with `x-ms-agentic-protocol: mcp-streamable-1.0`. Either way a **custom connector + connection reference** is created in the agent's solution.
3. **For org-wide/governed distribution**, use the **Agent 365 BYO MCP server** flow: the developer registers the remote server with the **Agent 365 CLI** (server URL, auth type — EntraOAuth or ExternalOAuth — and declared tools), which routes it through the **Agent 365 Tooling Gateway**; a tenant admin then **reviews and approves in Microsoft 365 admin center → Agents → Tools → Requests** and grants the required Entra permissions. Once approved (propagation up to ~30 min), it appears in Copilot Studio via **Tools → Add a tool → MCP Server → Pick from registry**. BYO MCP is **preview**; supported clients are Copilot Studio, VS Code, Claude Code, GitHub Copilot CLI (Foundry and M365 declarative agents not yet supported). Note: the CLI's `approve`/`block`/`package` commands were removed — approval now happens entirely in the admin center. (Microsoft Learn, manage-tools-for-agent + develop-mcp CLI reference, 2026.)
4. **DLP classification:** classify the custom connector into your DLP data groups (Business), keep M365 data connectors in Business, quarantine HTTP/custom/AI in Non-Business/Blocked, and use ACP to allow only this vetted server. Remember: **allow/block is per-server; no per-tool DLP** — so scope the app registration tightly (`Sites.Selected`) as your real least-privilege boundary.
5. **Versioning/update story:** tool changes are picked up dynamically (no agent republish needed for tool add/remove). But connector edits and cross-environment promotion require the connector to be in its own solution; iterating the server contract means re-importing/updating the connector and, for BYO, potentially re-approval.

## Recommendations
1. **Commit to build-new.** Scaffold a TypeScript MCP server (official SDK, stateless Streamable HTTP) with the discrete tool set in §5. Treat `reconcile_workbook_vs_repository` as the MVP centerpiece; ship it first against a single client before generalizing.
2. **Architect around path addressing + `$batch` + delta + Excel persistent sessions from day one.** These four techniques directly retire Pain Points #1, #2, #5, #6, #7. Persist deltaLinks and a file index in Azure Table Storage.
3. **Host on Azure Container Apps** (min replicas 1, `/health` GET, stateless). Use Azure Functions Flex Consumption only if scale-to-zero economics matter and you accept preview status. **Do not default to Cloudflare Workers** here despite your preference — the Graph/Excel-session model fits Node-native Azure better; revisit Workers only if cost/edge latency becomes a hard requirement and you externalize all session state.
4. **Register the Entra app with `Sites.Selected`** scoped to the Technology Success site as your least-privilege boundary (this is your real security control since DLP is per-server only). Use application permissions for deterministic autonomous runs.
5. **Publish via the MCP wizard for dev/test; graduate to Agent 365 BYO MCP registration for governed org-wide use** once the reconciliation engine is stable. Put the custom connector in its own solution so it is portable across environments.
6. **If (and only if) you hold M365 Copilot licenses, add Work IQ SharePoint MCP as a complementary primitive layer** for search/sharing/labels, keeping reconciliation/inventory/bulk-ops in your custom server.
7. **Design every tool as plan-then-execute** to preserve determinism/auditability; return structured diffs the LLM cannot alter.

**Benchmarks that would change these recommendations:**
- If Microsoft ships a **first-party reconciliation/batch-inventory tool** in Work IQ SharePoint (watch the "Work IQ SharePoint reference" doc), reduce your custom surface to the reconciliation delta only.
- If **per-tool DLP granularity** ships (watch ACP release notes), you can relax the `Sites.Selected` scoping and expose broader tools.
- If **Azure Functions self-hosted MCP goes GA**, prefer it over Container Apps for scale-to-zero cost.
- If your tool count across custom + Work IQ servers approaches **~25–30 in one agent** (Microsoft's recommended ceiling under the 128-tool hard cap), split into a hub-and-spoke multi-agent pattern (you have prior experience here) to preserve orchestration accuracy.

## Caveats
- **Preview vs GA flags:** Work IQ SharePoint MCP tool layer = **preview** (tool names/params may change; Microsoft warns against hard-coding dependencies). Agent 365 + BYO MCP = **preview**. Azure Functions self-hosted remote MCP = **preview**. Azure Container Apps MCP hosting docs are GA-track (dated 2026). Copilot Studio MCP integration + M365 declarative-agent MCP = **GA**. Work IQ API and ACP = **GA** (June 2026).
- **Excel throttling is workload-dependent, not a flat number** — the 5,000/1,500 per-10s figures are ceilings; heavy range/insert operations 429 far sooner. Build sequential-per-workbook access and `Retry-After` backoff into the reconciliation tool.
- **The 5 MB read cap on Work IQ SharePoint file reads** (and community servers) is a real constraint if any report files are large; your custom server using Graph directly can stream larger files but should still respect Graph limits.
- **A forward-looking MCP spec revision (mid/late 2026)** reportedly removes the initialize handshake and session IDs; this is sourced only from non-official blogs and is unconfirmed — verify against modelcontextprotocol.io before depending on it. The official MCP TS SDK stateless mode already insulates you from most of this.
- **Cloudflare limits cited** (10 ms free / 5 min paid CPU; 6 concurrent connections; 10,000 subrequests) are from Cloudflare docs dated July 2026 and are subject to change.
- Several community GitHub servers are **single-maintainer** and some rely on **app-only auth that Microsoft is deprecating in April 2026** — another reason not to fork them.
